#+TITLE: Context-Aware Transcription for Freestyle on Linux
#+DATE: [2026-07-28 Tue]
#+AUTHOR: Robert Krahn
#+FILETAGS: :freestyle:dictation:asr:context:linux:

* Goal

Make Freestyle transcribe technical speech on this machine (NixOS, GNOME 50.1,
Wayland) with Wispr Flow quality by feeding per-dictation desktop context into
both recognition and cleanup.

Success looks like: dictating into wezterm, Emacs, or a browser produces the
exact spelling and capitalization of identifiers, filenames, and commands that
are visible in the destination application, with end-to-end latency (stop
speaking to pasted text) around one second.

Non-goals for now: other platforms, other compositors, screenshot OCR.

* Decisions (alignment session, 2026-07-28)

1. *Architecture: upstreamable seam + plugin.* The core patch stays small and
   generic: one new pre-recognition plugin hook, one shared resolver, a
   cleanup context seam, and a handful of quality fixes. All collectors ship
   in a context plugin. Chosen over fork-first core integration.
2. *Terminal context: ASR + cleanup, redacted.* A redacted tail of the
   visible wezterm pane becomes Deepgram keyterms and cleanup context.
3. *Emacs is crucial.* Collected via =emacsclient= against the running Emacs
   server. Priority order: text visible in Emacs windows first, then other
   open buffers (lower rank).
4. *Cleanup on with OpenAI gpt-5.6-luna* (reasoning disabled, cached prefix).
5. *Plan review only for now.* Implementation starts after Robert reviews
   this document.

A welcome consequence of decision 1: because Freestyle plugins run inside the
server process, and the server runs in-process on this machine (in-session,
with D-Bus, PATH, and sockets), the collectors execute server-side at the new
hook. The entire client-side capture-and-transport machinery from the
fork-first draft (multipart switch, Streamer hold-start join, IPC capture
service, snapshot fields on three client requests) disappears. A remote
server degrades gracefully to no context, which is acceptable and documented.

* The one design idea

#+BEGIN_QUOTE
A new pre-recognition hook lets a plugin produce one bounded ContextSnapshot
per dictation. One core resolver turns that snapshot plus the user's
persistent vocabulary into both the ASR bias and a cleanup context block.
#+END_QUOTE

The hook contract is snapshot *production* only. Extraction, ranking,
merging, budgets, and redaction live in the core resolver, so provider limits
and safety have one authoritative home. Within one dictation, ASR and cleanup
read the same latched snapshot and can never disagree about spellings.

* What recon established (2026-07-28)

Condensed findings from a full codebase survey, a machine probe, and an

** Pipeline structure

- Batch: =POST /api/transcribe= (=apps/server/src/routes/transcribe.ts=). The
  =beforeTranscribe= hook fires here only. A plugin =bias= currently
  *replaces* the DB vocabulary, deliberately, at two sites
  (=transcribe.ts:404-410= BYOK, =transcribe.ts:271-273= cloud path).
- Streaming: persistent WS =/stream= (=apps/server/src/routes/stream.ts=). The
  client sends JSON control messages plus raw 16kHz s16le PCM binary frames.
  =start= / =context= / =commit= may carry a =context= string (=cancel= does
  not). The server resolves provider, model, language, and vocabulary bias
  itself in =resolveStreamConfig()= (=stream.ts:83-124=). No transcription
  hook runs before the provider session opens. This is the central gap.
- Keep-warm: Deepgram, ElevenLabs, and OpenAI upstream sockets open at WS
  connect and are reused across recordings when the config fingerprint
  (provider, model, language, bias) is unchanged (=stream.ts:799-827=,
  =lib/streaming/session-policy.ts=). Audio arriving while an upstream
  connects is buffered, up to 500 chunks which is roughly 40 seconds
  (=stream.ts:743-760=), and flushed on ready. An awaited context step before
  the provider opens therefore loses no audio.
- Deepgram streaming: keyterms ride the WS URL query string
  (=lib/streaming/providers/deepgram.ts:64-79=), so bias is fixed at connect
  time and =setContext= is not implemented. Freestyle caps streaming keyterms
  at 25 (=lib/vocabulary-bias.ts:18=). Commit sends ={"type":"Finalize"}=.
- Vocabulary: SQLite =vocabulary= table, merged into provider-specific bias in
  =lib/vocabulary-bias.ts= (prompt text for OpenAI-style, keyterms for
  Deepgram nova-3, keywords for nova-2, Soniox context object, and so on).
  Terms load longest-first and caps keep the first N, so list order is the
  priority mechanism. This per-provider mapping is solid and stays as-is.
- Cleanup: one blocking non-streaming =generateText= at temperature 0 via the
  AI SDK (=packages/stt/src/post-process.ts=). Prompt assembly in
  =lib/editor/prompts.ts= = intensity preset + language block + destination
  tone block. The prompt contains *no* vocabulary, dictionary, or context
  text. App context only routes the tone destination. Dictionary replacements
  run after the LLM. The BYOK cleanup call has no timeout, but
  =postProcess()= already accepts an =AbortSignal= that no caller passes, so
  the fix is wiring, not plumbing. Cleanup is silently skipped when the model
  id is unknown to the remote models.dev registry
  (=routes/models.ts:293-318=).
- Multi-segment dictations: later segments are transcribed with
  =x-skip-post-process= and the *only* cleanup happens in the client-driven
  merge call =POST /api/post-process= (=app.tsx:317-353=,
  =routes/post-process-route.ts=). Context must reach this route too.
- REST fallback: when the streaming commit times out (15s) or errors, the
  client salvages the recording via =restFallbackTranscribe= posting the
  buffered WAV to =/api/transcribe= (=app.tsx:467-521=). With server-side
  collection this path needs no special handling: the hook runs fresh on the
  fallback request.
- App context: the client captures the frontmost app per recording, but only
  when LLM cleanup is on and at least one tone is active
  (=apps/electron/src/renderer/src/lib/cleanup-app-context.ts=,
  =lib/post-process.ts:144-153=). The server additionally nulls it under the
  same condition (=effectiveAppContext()=). Both gates must be decoupled so
  ASR context works regardless of cleanup settings.
- Client dictation flow: evdev hotkey binary -> Electron main
  =sendHotkeyDown= (=apps/electron/src/main/index.ts:2517=) -> pill window
  (=focusable:false=, shown with =showInactive()=, never steals focus) ->
  renderer captures mic and streams PCM. Client streaming commits are
  serialized (re-record defers while a commit is pending,
  =app.tsx:1270-1276=).
- Paste is clipboard + synthetic Ctrl+V via a uinput helper, with portal and
  wtype fallbacks (=paste.ts=). Works on this machine (user is in =input= and
  =uinput= groups).
- Plugins run in the server process (Electron main hosts no registry). Hooks
  have no timeout today. Plugins are trusted in-process code with full Node
  capabilities, which is exactly what the collectors need.
- Latency instrumentation: pipeline logging is on by default
  (=FREESTYLE_LOG_PIPELINE_LATENCY=), but the stt/handoff/llm/e2e breakdown
  only fires on the Soniox fast-handoff path. The Deepgram path logs totals
  only, so the instrumentation needs a small extension before cleanup latency
  can be measured.
- Streaming is always active when the provider supports it: =/stream= mounts
  unconditionally and the renderer builds the Streamer unconditionally. The
  old =streaming_audio= gates in lore are stale.

** This machine (verified by probe plus adversarial re-check)

- GNOME Shell 50.1 on Wayland. =swaymsg= absent,
  =org.gnome.Shell.Introspect.GetWindows= returns AccessDenied, X11 fallback
  useless for Wayland windows. *Frontmost-app detection is currently broken
  here.*
- The proven fix exists on this machine: VibeTyper's GNOME Shell extension
  (=com.vibetyper.FocusBridge=, =GetActiveWindow()= -> JSON with appId,
  title, wmClass, pid). It is dead only because its =metadata.json= declares
  shell-version up to 49. Every API it calls was verified present in Shell
  50.1 girs, so a metadata bump is the entire port.
- AT-SPI: the bus works mechanically (address resolvable, registryd running,
  raw busctl tree walks and =GetText= calls answer in ~10ms). But with
  =toolkit-accessibility= off, *zero running applications expose focused
  text*, and two never will: Emacs's editing area implements no AT-SPI Text
  interface (only its GTK window chrome is exposed, verified by full tree
  walk), and wezterm (the running terminal) is not GTK/VTE and never
  registers on the a11y bus. AT-SPI is therefore a collector for browsers,
  Electron apps, and GTK3 apps only, contingent on flipping
  =toolkit-accessibility= on.
- Terminal: *wezterm*. It has its own CLI (=wezterm cli get-text=) that
  returns pane text directly. That is the terminal collector, no AT-SPI
  needed.
- Emacs: pgtk 30.2, server socket up. =emacsclient --eval= round trip
  measured at 4ms. This is the Emacs collector.
- No dbus npm package anywhere in the dependency tree. =dbus-next= is pure JS
  but unmaintained since 2021, needs a Node 24 compatibility check before the
  AT-SPI phase commits to it. (The plugin's FocusBridge query can use =gdbus=
  or =busctl= subprocess calls instead of a library if simpler.)
- Dev shell: =flake.nix= is an empty =mkShell {}=. Node v24 available, pnpm
  only via the =packageManager= pin (corepack), no bun.
- The repo =.env= (DEEPGRAM_API_KEY, OPENAI_API_KEY) is *inert*: nothing
  loads it. Provider keys live in the =api_keys= SQLite table, entered
  through the app settings UI.

** Model research (verified against current docs)

- ASR: *Deepgram nova-3 streaming* on =wss://api.deepgram.com/v1/listen= is
  the clear pick: sub-300ms streaming, per-request keyterm biasing as
  repeated =keyterm== query params (limit 500 tokens, roughly 100 words,
  multi-word phrases allowed, no weights), an explicit =Finalize= flush for
  push-to-talk, =smart_format= / =punctuate= / optional =dictation= mode, at
  $0.0048/min. Keyterm prompting now also works multilingually on nova-3.
  Sources: https://developers.deepgram.com/docs/keyterm,
  https://developers.deepgram.com/reference/speech-to-text/listen-streaming
- OpenAI has no competitive streaming ASR for this feature: the realtime
  =gpt-realtime-whisper= rejects the =prompt= parameter and costs 3.5x more.
  =gpt-4o-mini-transcribe= (batch, supports =prompt=) is a reasonable
  *fallback* for the batch path.
- Cleanup LLM: *OpenAI gpt-5.6-luna* (current low-latency tier of the GPT-5.6
  family): streaming, prompt caching ($0.10/M cached input), structured
  outputs, reasoning effort selectable down to =none=. Verify at integration
  time that =none= works on luna, else measure time-to-first-token. Budget
  fallback: =gpt-4.1-nano=. Source:
  https://developers.openai.com/api/docs/guides/latest-model.md
- Deepgram Flux is the wrong tool here (voice-agent turn detection). Noted as
  a later option only because its keyterms are updatable mid-stream.

* Design

** Data flow

#+BEGIN_SRC text
client: hotkey down → pill (no focus steal) → mic → WS start {context}
                     │
server /stream "start"
  ├─ hook: resolveRecognitionContext (plugin, bounded await ≤250ms)
  │    plugin collectors (all local, in the server process):
  │      ├─ focused window   ← FocusBridge GNOME extension (D-Bus)
  │      ├─ terminal text    ← wezterm cli get-text   (wezterm focused)
  │      ├─ editor context   ← emacsclient --eval     (Emacs focused)
  │      └─ focused text     ← AT-SPI                 (browsers etc., later)
  │    → ContextSnapshot (bounded, latched for this dictation)
  ├─ core resolver: extract terms, rank, redact,
  │    merge with DB vocabulary → ranked term list + cleanup block
  ├─ buildAsrVocabularyBias(provider, model, terms)   [existing mapping]
  └─ open Deepgram WS with keyterms  (audio buffered meanwhile)
                     │
commit → Finalize → raw transcript
  └─ postProcess(raw, appContext, {recognitionContext})   [same snapshot]
       → prompt gains a context block: preserve matching spellings,
         never insert unspoken terms
  └─ dictionary replacements → paste
#+END_SRC

The batch route runs the same hook per request. The multi-segment merge
route (=/api/post-process=) runs the hook fresh at merge time (the user is
pasting into the same destination, and re-running is simpler than a
cross-request snapshot store).

** The core patch (upstreamable)

Kept deliberately small and provider-generic. No collector knowledge.

*** New hook: =resolveRecognitionContext=

#+BEGIN_SRC typescript
// packages/sdk/src/hooks.ts
resolveRecognitionContext?: Handler<
  {
    readonly providerId: string;
    readonly modelId: string;
    readonly streaming: boolean;
    readonly appContext?: AppContext;   // what the client sent, if anything
  },
  { snapshot?: ContextSnapshot }        // plugins fill fields, merged by field
>;
#+END_SRC

Dispatched in both routes before the provider session opens: batch before
=provider.transcribe=, streaming inside the =start= handling before
=connectUpstream= (audio buffers during the await, verified safe). Because
this hook sits on the recognition critical path, the host wraps it in a
bounded await (~250ms): on timeout the dictation proceeds without a snapshot
and the timeout is logged. This is the first hook with a timeout, which is a
deliberate part of the contract.

=ContextSnapshot= (zod schema in =packages/validations=, re-exported by the
SDK). All fields optional, all bounded at parse time, treated as untrusted:

#+BEGIN_SRC typescript
interface ContextSnapshot {
  capturedAt: number;
  app?: { name: string; windowTitle?: string; wmClass?: string; url?: string };
  terminal?: { paneText: string };            // ≤3000 chars, pane tail
  editor?: {
    file?: string;
    language?: string;
    visibleText?: string;                     // ≤2000 chars, visible windows
    symbols?: string[];                       // ≤100, imenu / defuns
    openBuffers?: string[];                   // ≤100 names, lower rank
  };
  focusText?: {                               // AT-SPI, later phase
    before: string;                           // ≤2000 chars before caret
    selected?: string;                        // ≤500
    after?: string;                           // ≤500
    role?: string;
  };
}
#+END_SRC

*** Core resolver: =lib/recognition-context.ts=

One authoritative home for everything between snapshot and provider:

1. Parse and bound the snapshot (zod).
2. Extract candidate terms deterministically from =terminal=, =editor=,
   =focusText=, and the window title: camelCase, PascalCase, snake_case,
   kebab-case, dotted names, paths, filenames, acronyms, mixed
   alphanumerics, plus quoted and backticked spans. No LLM call.
3. Rank: source weight (editor symbols > selection > visible editor text and
   pane tail > open buffer names > window title), frequency, specificity
   (length, mixed case, digits). Drop bare common English words.
4. Redact secrets (high-entropy tokens, =KEY=value= pairs, PEM markers) from
   terms and excerpts. Runs on every source uniformly since terminal output
   is the riskiest.
5. Merge: static DB vocabulary always first, then plugin =beforeTranscribe=
   bias terms, then contextual terms by rank, deduped case-insensitively
   with original casing kept. Order is priority: the existing =capTerms=
   keeps the first N.
6. Return ={ terms, noteText, cleanupBlock }= where =cleanupBlock= carries
   the top exact spellings and a short excerpt for the prompt.

=resolveAsrVocabularyBias()= gains optional snapshot and plugin-terms
parameters and calls the resolver. =buildAsrVocabularyBias()= (per-provider
mapping) is unchanged.

Plugin bias contract change (explicit, not incidental): today a plugin
=bias= fully replaces the DB vocabulary at two route sites
(=transcribe.ts:404-410= and =:271-273=). Both change to merge through the
resolver. The SDK doc says "override or augment", so this narrows to
augment. Documented in the SDK.

*** Streaming route changes

- The hook's snapshot is latched per recording at =start= and passed into
  =connectUpstream= and the finalization closure (no re-reading mutable
  route state at final time, no double config resolution).
- The resolved bias joins the config fingerprint, so a changed term list
  closes and reopens the warm Deepgram socket on =start=. That reconnect
  (~100-300ms) overlaps with speech and audio is buffered, so the
  commit-to-paste tail is untouched. With context enabled this is
  effectively a reconnect per recording. Warm reuse survives across
  identically context-free recordings. Measured in Phase 2, mitigations in
  Phase 4.
- Raise the Deepgram streaming keyterm cap from a fixed 25 to a URL-length
  budget (Deepgram's real limit is 500 tokens). Verify the handshake.
- Decouple context from cleanup settings on both sides
  (=effectiveAppContext()= server-side, =cleanup-app-context.ts=
  client-side). ASR context gets its own setting.

*** Cleanup changes

- =postProcess()= accepts the resolved =cleanupBlock= and passes it to
  =buildRewritePrompt()=, which appends a context section to the *user*
  prompt (following the existing injection-guard + =<transcript>= pattern):
  a =<context>= block with exact spellings and the excerpt, explicitly
  marked as untrusted reference material, with two hard rules: preserve
  identifier spellings, capitalization, paths, and commands that match
  context terms, and never insert a term merely because it appears in
  context.
- =/api/post-process= (multi-segment merge) dispatches the hook fresh and
  feeds the same resolver, so merged dictations are covered.
- Configure OpenAI =gpt-5.6-luna= as the cleanup model. Add per-model
  =providerOptions= for OpenAI in =lib/llm/registry.ts= to disable reasoning
  (the Groq entries show the pattern) *and* implement a =prewarm= hook for
  the OpenAI provider entry: prewarm currently exists only for Groq, so the
  latency budget's warm-TLS line does not exist for OpenAI yet.
- Wire an =AbortSignal.timeout= (about 10s) into the cleanup call, falling
  back to the raw transcript. The signal parameter already exists in
  =packages/stt=, nothing passes it.
- Structure the prompt so the static prefix (system + instructions) is
  cacheable and the per-dictation context block comes last.

** The context plugin (this fork, =plugins/desktop-context/=)

A server-process plugin implementing =resolveRecognitionContext=. It runs
collectors *locally in the server process* (which is in-process in Electron
on this machine, on the session bus, with the user's PATH). Each collector
has its own timeout and failure is always graceful (missing field, never a
blocked dictation). Collector dispatch keys off the focused window.

*** Focused window: Freestyle FocusBridge GNOME extension

Adopt the FocusBridge pattern as a Freestyle-owned extension in this repo:
=com.freestyle.FocusBridge=, =GetActiveWindow()= returning ={app, title,
wmClass, pid}=, metadata covering shell-version 50 (verified: nothing else
needs porting). The plugin queries it over the session bus (via =gdbus= or
=busctl= subprocess, no npm D-Bus dependency needed for v1). Also wire it as
the first Wayland probe in the client's =getLinuxFrontmostApp()=
(=index.ts:1014=) so the existing appContext and tone routing work again on
GNOME 50. Install step documented for NixOS.

*** Terminal: wezterm CLI

When the focused window is wezterm: =wezterm cli get-text= for the active
pane, strict timeout, trailing bounded chunk into =terminal.paneText=.

*** Editor: Emacs bridge

When the focused window is Emacs: =emacsclient --eval= (measured 4ms)
calling a function from =integrations/emacs/freestyle-context.el=:

- current buffer file name and major mode,
- text of *visible windows* (all windows in the selected frame, bounded),
  highest priority per the alignment decision,
- imenu symbol names near point,
- names/files of other open buffers, lower priority.

AT-SPI can never provide this: Emacs's editing area exposes no Text
interface. VS Code/Cursor/Zed bridges are out of scope until one is in use.

*** Focused text: AT-SPI [later, value-gated]

For browsers, Electron apps, and GTK3 apps only. Requires flipping
=toolkit-accessibility= on (today zero running apps expose focused text) and
a D-Bus client library (verify =dbus-next= on Node 24 or pick a fork).
Bounded traversal seeded by the focused window's pid, text around the caret,
warm event-driven cache only if measurement demands it. Build only if the
Phase 2 eval shows a real gap on browser/Electron dictation.

** Privacy and safety constraints

- Snapshot is bounded, short-lived, never persisted, never in analytics.
- Redaction happens in the core resolver, so it applies regardless of which
  plugin produced the snapshot.
- Captured text is untrusted: never in the system prompt, only in a
  delimited user-prompt block flagged as reference data.
- Logs record term counts and collector latencies, not captured text.
- Analytics keep the existing rule: no window titles, URLs, or captured text
  in PostHog, only counts and source flags.

* Latency budget

Target: commit (hotkey release) to pasted text under ~1.2s. The context work
must all sit off this path.

| stage                           | budget       | mechanism                                  |
|---------------------------------+--------------+--------------------------------------------|
| hook (collectors, at start)     | ≤250ms bound | awaited before upstream open, audio buffers |
| Deepgram reconnect w/ keyterms  | ~100-300ms   | overlapped with speech, audio buffered     |
| Deepgram Finalize tail          | ~100-300ms   | existing commit path                       |
| cleanup LLM (gpt-5.6-luna)      | ~300-700ms   | reasoning none, cached prefix, new prewarm |
| paste                           | ~50-350ms    | existing uinput helper + settle delay      |

Expected hook reality: FocusBridge and emacsclient are single-digit
milliseconds, wezterm CLI tens of milliseconds. The 250ms bound is a safety
ceiling, not a target.

Measurement: pipeline logging is on by default but the stt/handoff/llm/e2e
breakdown currently fires only on the Soniox path. Phase 1 extends
=includeTimings= to the Deepgram streaming path and adds hook/collector
timings, otherwise the cleanup latency claims cannot be verified.

* Evaluation

Fixed corpus, recorded once, replayed through =POST /api/transcribe= (and a
scripted WS session for the streaming path) with snapshot fixtures injected
via a test plugin. A small script in =scripts/eval-context/= drives the
matrix and diffs against reference texts. It hits live providers
deliberately and is run manually, not in vitest (matching the repo
convention that provider paths get manual e2e verification).

Corpus (~25 utterances, from the earlier bake-off list plus this repo's own
identifiers): =getScreenContext=, =AccessibilityDumpResult=, =RUST_LOG=,
=resolveAsrVocabularyBias=, =pnpm --filter @freestyle-voice/server test=,
paths like =apps/server/src/routes/stream.ts=, HTTP codes, keyboard
shortcuts, plus a few plain-English controls (to catch context-induced
regressions and unspoken-term insertion). Terminal-flavored subset (dictating
follow-ups to an agent about visible command output) and Emacs-flavored
subset (dictating about code in the visible buffer).

Metrics per config (no context / vocab only / context to ASR / context to
ASR + cleanup / plus editor or terminal context):

1. Technical-term recall in the raw transcript.
2. Exact spelling and capitalization in the final text.
3. Cleanup corruption rate (raw had it right, cleanup broke it).
4. Unspoken-term insertion rate (context term appears without being spoken).
5. Commit-to-final latency, plus hook and connect timings.

Main hypothesis to confirm: context in ASR plus cleanup materially beats
cleanup-only context.

* Risks

- GNOME updates break the Shell extension (metadata churn). Accepted: it is
  a 20-line extension we own, and the failure mode is graceful (no window
  context).
- A remote Freestyle server cannot run the collectors. Accepted and
  documented: the hook simply returns nothing there.
- Deepgram reconnect per recording forfeits the warm-session benefit
  whenever context is present. Measured in Phase 2, mitigations in Phase 4.
- Keyterm URL length limits on the WS handshake. Bounded budget + handshake
  verification in Phase 1.
- Prompt injection via captured text (terminal output especially). Delimited
  untrusted block + explicit instructions + eval metric 4 (insertion rate).
- gpt-5.6-luna latency without reasoning is unverified. Measured in Phase
  0/1, fallback =gpt-4.1-nano=.
- The bounded hook await is a new contract on the recognition path. Ceiling
  250ms, logged, dictation always proceeds without context on timeout.
- AT-SPI value is speculative on this machine. Contained: Phase 3 is
  value-gated and defaults off.

* Remaining open questions

1. Should the plugin bias "replace" escape hatch survive as an explicit flag
   when the semantics narrow to "augment"? Default answer: no, add it only
   when a plugin needs it.
2. Hook naming: =resolveRecognitionContext= (used here) vs something
   shorter. Decide at SDK-doc time, before the upstream proposal.
3. Whether the multi-segment merge should reuse the first segment's latched
   snapshot instead of re-running the hook. Current answer: re-run (simpler,
   destination unchanged). Revisit only if eval shows divergence.
